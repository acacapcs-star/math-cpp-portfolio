### 1. Bingo（小竹 Bingo）

在此題中，我一開始的直覺作法是,
每次叫到一個數字時,就重新走訪整個二維陣列,
逐一檢查所有座標,確認該數值所在的位置。

由於盤面本身是以二維陣列儲存，
空間複雜度為O(N²),
而若每次叫號都重新掃描整張盤面，
時間複雜度同樣會達到O(N²)

考量到此題會有多次叫號(最多可達數百次),
這樣的作法會造成大量重複的檢測。
因此我在讀入資料時,
額外建立一個<數值→座標(x,y)>的對照結構,
先把每個數字在盤面中的位置記錄下來。

這樣在之後每次叫號時,
只需要直接查詢該數字對應的座標，
即可立刻更新該行、該列(以及斜線)的狀態,
避免反覆掃描整個盤面

**【複雜度分析】**
- 時間複雜度：雖然時間複雜度並沒因為優化而改變,但透過
  "預處理"這個priority成功地“大幅降低”了重複掃描的次數
- 空間複雜度：使用 N * N 的二維陣列與額外的座標對照結構
  =>整體為O(N²)

### 2. Flood（淹水啦）

在一開始構思這題時，我的直覺作法是：
嘗試先假設每一層高度都能夠累積一層水,
再逐步判斷哪些區域會實際形成淹水。

然而在進一步分析後發現，
這樣的想法只適用於高度分布較單純==他的高度都是“統一為1層”的情況之下。
當地形的橫向面積很大,但各位置的高度不一致時,
是否能形成淹水,取決於「最低高度」是否能夠被"完全包圍"，
而不是"單純"看某一層是否存在空間。

因此在實作上，
必須從整體高度的"最低層"開始去探討,
逐層向上模擬水位的上升,
並確認在每一個高度下,
是否存在可以讓水流向外部的通道。
==假如已經被填滿,就必須要在判斷完成之後自動跳過那一格,避免重複計算到
只有當該高度的所有可連通區域皆被封閉時,
該區域才會被判定為真正的淹水區域,並開始進行累積。

這樣的作法避免：
”單一高度條件“就做出判斷,
而是透過由"低"到"高"的整體檢查,
確保每一筆淹水的判定都符合實際"地形的限制條件"。

**【複雜度分析】**
- 時間複雜度：需要依高度層逐步進行檢查,整體仍屬於多次"遍歷地形"的相應模擬過程
- 空間複雜度：主要使用地形高度的二維結構與輔助標記陣列,因此可視為O(N²)

### 3. Dark Particle（暗粒子）

在撰寫此題的初期,我的作法是分別紀錄兩顆粒子的"初始位置"與"速度",
並假設它們在運動過程中皆為等速直線運動。
因此在每一個固定的 time lapse 中,
只需依據速度"方向與大小",更新對應的”單位向量“即可。

實作碰撞判斷時,我一開始只在每個時間點檢查是否重疊,
後來才意識到這樣會錯過真正的碰撞瞬間。
一開始僅有考慮速度並“不足以”完整描述粒子的運動狀態,
還必須進一步“處理邊界條件”,例如上下左右的那種最邊緣的部分
當粒子碰觸到邊界時，會發生反彈,
且在不考慮"摩擦力"與"能量之耗損"的前提下,
反彈後的"運動距離"==原本的"起始"座標＋"原本移動距離的固定增加量"
以此確保在任意的t秒後仍能計算出正確的位置,而不會隨意展示出偏差

此外，當兩顆粒子"發生碰撞"時,
其行為可視為"完全"彈性碰撞,
亦即兩者會互相交換"速度"&"方向"。
因此在最後時,我有增加一段程式:
"額外"加入此判斷機制,
優先計算粒子之間發生碰撞的"精確時間點",
並在該時刻更新速度狀態,

以避免因離散時間步長造成位置或速度上的誤差。
可以在維持簡潔模型的情況下,
同時"正確處理邊界反彈與粒子碰撞",
使整體模擬結果更加"精確且穩定"。

**【複雜度分析】**
- 時間複雜度：主要依時間步進進行模擬，並在每個步驟中進行常數次判斷
- 空間複雜度：需紀錄固定數量
  兩顆粒子:
  位置、速度與相關狀態,所需空間不隨輸入規模改變,
  因此可視為O(1)的空間使用情況。

### 4. Cube 3D（立體模擬）

當我一開始處理三維空間問題時，我發現這題與高二下數學的空間概念有明顯的關聯性。
然而在實作過程中，我也很快意識到，不能單純沿用二維平面中的判斷方式。
若只計算平面的 i、j，而沒有納入第三個方向 k，
在處理「穿越中心點」的情況時，便容易忽略其他需要計算的方向。

例如在計算通過中心點的斜向直線時，
若沒有完整考慮三維空間中的各個切片，
就可能造成部分方向未被記錄，或出現重複計算的情況。
因此在設計時，我必須確保每一個切片與面向都能被納入判斷，
包含垂直、水平，以及不同方向的斜線。

在實作過程中，我先明確定義三維空間中的各個方向，
並統一座標的起始基準。
我將立方體的一個角落（左上角）設為 (0,0,0)，
再依照不同面向進行分類，
同時在每一次延伸時確認座標是否仍位於合法範圍內，
以避免因判斷不足而造成重複或錯誤計算。

在這個分類的過程中，我逐漸理解到「空間向量」在三維問題中的重要性。
相較於平面座標只需考慮 x、y，
三維空間中必須同時處理 x、y、z 三個方向，
若未先固定向量方向，便容易在不同情況下混淆或重複判斷。

最終在程式中，我以 (0,0,0) 為基準，
分別沿著垂直方向、平面對角線以及立體對角線進行檢查。
透過這樣的方式，
我能夠有系統地枚舉所有可能的方向，
並判斷在三維空間中實際存在多少組符合條件的對角線組合。

**【複雜度分析】**
- 時間複雜度：立方體中共有N³個座標點,方向數量為固定常數,因此整體時間複雜度可視為 O(N³)
- 空間複雜度：主要儲存立方體的三維陣列,所需空間與輸入大小成正比，為 O(N³)

### 5. RGB Image Processing（RGB 檔案）

在撰寫此題時,我一開始將RGB三個顏色通道分別以三個二維陣列儲存,
使每一個像素的位置(i,j)都能對應到其R、G、B三個數值。

在初始構想中，
我先逐一掃描整張影像，
計算每一個像素與指定顏色(r0,g0,b0)之間的差異,
並以三個通道的<絕對差總和>作為"顏色距離"的判斷依據。
若該像素的顏色距離小於等於"d",
則將其座標記錄為「目標像素」。

在實作過程中，我將「顏色判斷」與「位置判斷」拆成兩個階段處理。
第一階段先找出所有符合顏色條件的像素位置，
並將其存入一個座標列表中。
第二階段再針對影像中的每一個像素，
檢查其是否位於任一目標像素的距離範圍內，
距離的計算方式採用座標的"曼哈頓距離"。
總之就是取座標差值的絕對值來計算距離。

透過這樣的拆解方式，
可以避免在同一輪中同時進行顏色與距離的重複計算，
讓程式流程更加清楚，
也更容易確認每一個判斷步驟是否正確。

**【複雜度分析】**
- **時間複雜度**：需先遍歷整張影像找出符合顏色條件的像素，
  再對每個像素進行距離檢查，整體約為 O(N²)
- **空間複雜度**：主要儲存 RGB 三個二維陣列與目標像素座標列表，
  為 O(N²)

## 學習重點與反思
在寫 code 的過程之中，
我從原本只能從表面的題目蒜皮來粗略地寫出一些較為 simple 的 logic，
到可以利用條列式的邏輯思維去拆解題目裡面的細節以及可能會有的特殊邊界感的範圍，
再到如何在原本較為混亂的迴圈之下，
學會如何有條理地去 rearrange 我原本較為混亂的代碼，
再利用特定的固定架構之下，
成功地讓我原本容易亂跳的思維變得更加乾淨利落。

在這樣的不同題型之下，
即便題目再複雜，conditions 再多，
其實都可以完美地分成四個塊：宣告、輸入、處理、輸出。

通常在宣告的情況之下，
我發現我最常使用的變數名稱莫過於 i、j、k/x、y、z。
至於其他的變數或型態，
只要是時常要做紀錄的，
通常會採用 ans、sum、cnt 等等的代號，
不但可以顯得濃縮，
又能夠立即看穿本意，
是個最重要的辨別法則。

當在做處理時，
假如發現原本的寫法複雜度過高，
即可利用預先設置的 void() 來解決此問題，
並且 function 寫在 main 的上方時，
也可以減少在解題時的眼花繚亂，
進而達到快狠準的好效果。

當然，比較複雜的題目不只會牽涉到一種算式，
因此我開始較為習慣使用 if、else 等架構來隔開判斷式。
而最重要的一環還是要先寫完整個架構之後，
先註解並說明每一段在做什麼，
再用 plug in 的方式去補上裡面較為細節的判斷。
